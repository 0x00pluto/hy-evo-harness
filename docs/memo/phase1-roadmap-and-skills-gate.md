**仅备忘，不是已排期承诺，也未在本仓实现。**

## 上线 Roadmap

围着「先卖得出去、账算得清」，不围着「先藏住提示词」。

### 第一期上线门槛

第一期范围仍以 [phase1-billing.md](phase1-billing.md) 为准：登录、买断、额度、网关转发模型并扣费；提示词本机拼。

建议用真实交易验收，而不是功能清单打勾。四条都过再开下一期：

1. 完成一单真实买断（或销售按手机号录入）  
2. 换机后同一账号仍能用  
3. 额度用完能充上  
4. 生成失败时额度会退  

### 上线后分期

| 期 | 目标 | 建议内容 | 触发条件 |
|---|---|---|---|
| **P1.5** | 钱从「能收」变成「自己收」 | 应用内自助买断 / 充值；管理后台（查用户、补授权、调额度、看流水）；用量与供应商成本看板 | 已有人付款，或销售每周都要改库 |
| **P2** | 产品变厚 | 小红书竖切加厚；第二个可卖插件；工作台余额 / 购买 / 错误单号入口 | 客户反复卡在某一步，或销售需要第二个 SKU |
| **P3** | 降低续费摩擦 | 额度月包（每月自动加额度，不是软件租金）；余额将尽提醒；按真实用量调附赠档位 | 充值包已有复购，但抱怨老要手动买 |
| **P4** | 团队与 B 端 | 席位、统一账单、管理员发授权；发票 / 合同价 | 有多账号团队愿意加价，而非个人「觉得应该有」 |
| **P5** | 配方上收（可选） | 高价值拼装迁网关；用户包装卸提示词 | 有稳定收入，且出现可证实的抄袭或泄密压力；否则继续本机拼 + 网关扣费 |

### 刻意后置

| 项 | 原因 |
|---|---|
| CDN 动态加载业务代码 | 运维复杂，不服务第一期与近路目标 |
| 加密壳 / 强混淆 | 不保障扣费，分散精力 |
| 一上来多插件市场分成 | 仍在自己卖自己的插件 |
| 公司席位先于自助支付 | B 端重，个人链路未验证时易空转 |

### 示意时间线

```text
现在 ──► P1 上线门槛（登录 / 买断 / 扣费 / 生图）
         │
         ├─► P1.5 自助支付 + 后台 + 成本看板
         │
         ├─► P2 插件加深 / 第二个付费插件
         │
         ├─► P3 月包与续费体验
         │
         ├─► P4 团队席位（有明确 B 端需求时）
         │
         └─► P5 配方上收（有证据再做）
```

### 如何判断没跑偏

每一期只问三个问题：

1. 这期能不能多一笔真实收入，或少一笔真实客服成本？  
2. 是否还守着「钥匙和账在网关、体验在本地」？  
3. 有没有为了「防抄」提前做了没有用户的重架构？  

P1 过关之前，主线就是收费备忘里的实现顺序；过关之后用支付、后台、第二个 SKU 把生意做宽，再用数据决定月包和团队版；配方上收放在最后且要有触发条件。

## 技能中心仓可借鉴路线

调研对象（本机路径，非本仓）：

`/Users/peng.zhi/Documents/Object/WeDAO/huyuan-ai-skills-gate`

### 它是什么 / 不是什么

| 是 | 不是 |
|---|---|
| 互远技能中心 Web 入口：Next.js + Vercel + Supabase | Dex Buddy 的 LLM 用量网关 |
| 手机号登录、企业 / 成员、技能目录、员工 API Key | DeepSeek / Replicate 转发 |
| 时间型会员订阅 + 支付宝自助开通 | 按次扣模型额度的钱包 / ledger |

对第一期：重叠在「账号 / 权益 / 支付 / 服务端校验」；**模型代理与额度流水要新建**。

### 值得借鉴

| 能力 | 线索（Gate 仓内） | 对 Dex 第一期的用处 |
|---|---|---|
| 栈形状 | Next.js App Router、Vercel、Supabase | 与「单独网关仓」一致，少重新选型 |
| 手机号 OTP | `POST /api/site/auth/sign-in/phone` 等；`docs/supabase-send-sms-hook-aliyun.md` | 登录主路径可对齐，不必另发明短信通道 |
| 支付入账 | `docs/payment-channel.md`；create / status / notify；`apply_membership_payment` | 前端禁止伪造 paid；幂等 `clientRequestId`；通道 Adapter——买断 / 充值自助时适用 |
| 权益快照 | whoami / validate 带 `entitled`（如 prd-00038）；`lib/membership-skill-access.ts` | 学「身份接口附带能不能用」；字段换成买断列表 + 余额 |
| 服务端闸门 | 员工 Key → validate；失败才装技能 | 对应：会话在宿主，烧钱前网关查买断；破解 UI 无效 |
| 文档习惯 | `docs/api-route-governance.md`、`docs/supabase-tables.md`、migration 规范 | 网关长大后靠文档约束路由与表 |
| 人工与自助同一权益模型 | 订阅 grant 与支付宝入账同一套 | 销售录入买断 + 以后自助买，共用 entitlements / 流水写入 |

一句话：**学登录、支付入账、权益快照、门禁；不要学「卖的是订阅装技能」。**

### 不要照搬

1. **没有用量钱包。** 会员是月/年订阅，不是按次 ledger。额度表、扣费、失败退回须新建。  
2. **没有模型代理。** Chat / 生图包装要在 Dex 网关自建。  
3. **组织 / 部门 / 邀请过重。** 第一期个人手机号 + 买断即可；团队席位属 P4。  
4. **凭证形态。** Gate 偏员工 API Key + CLI；桌面第一期用会话 + refresh 更贴，不必先上员工 Key。  
5. **勿整仓 fork。** 技能目录、同步、邀请、GEO 等与第一期无关；宜**新建瘦网关**，从 Gate 抽模式与少数模块。

### 建议抽用顺序（对接第一期实现）

1. **登录：** Supabase 手机 OTP + 阿里云发信 Hook 的配置与路由形状  
2. **数据：** Supabase + migration 习惯；自建 entitlements / wallets / ledger（或等价）  
3. **权益查询：** 给宿主的「我是谁 + 买了哪些插件 + 余额」快照（学 whoami，换字段）  
4. **支付（P1.5）：** 对齐 payment-channel 的 create / status / notify + 服务端 apply；P1 销售录入可先后台 / RPC  
5. **模型层：** 在新仓自建；Gate 无现成实现  

### 结论

有参考价值，主要在账号、短信、支付入账、服务端权益门禁；对「调模型 + 扣费」只提供底座。当作兄弟项目的最佳实践样本，不要当作复制粘贴即可上线的 Dex 网关。
